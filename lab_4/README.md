# Обработка лабораторных проб

REST-сервис лаборатории: приём проб от заказчиков, назначение методик анализа, ввод и подтверждение результатов
измерений, завершение исследований. Данные хранятся в PostgreSQL.

**Стек:** Java 21, Spring Boot 4.1.1 (Web MVC, Data JPA, Spring Security), PostgreSQL, Lombok, Maven.

## Предметная модель

| Сущность | Путь API | Назначение |
|---|---|---|
| Пользователь (User) | `/api/users` | Заказчик проб |
| Проба (Sample) | `/api/samples` | Материал, заказчик, дата получения (ставит сервер), статус |
| Методика (AnalysisMethod) | `/api/analysis-methods` | Допустимый материал, диапазон значений, максимальный разброс |
| Исследование (Analysis) | `/api/analyses` | Проба + методика, статус, итоговое среднее |
| Измерение (Measurement) | `/api/measurements` | Значение, время (ставит сервер), признак подтверждения |

Для каждой сущности доступны `GET` (список), `GET /{id}`, `POST` (201), `PATCH /{id}`, `DELETE /{id}` (204).

**Статусы.** Проба: `RECEIVED` -> `IN_PROGRESS` -> `COMPLETED` или `REJECTED`. Исследование: `IN_PROGRESS`,
`COMPLETED`, `CANCELLED`. Статус пробы вычисляется по её исследованиям и вручную, кроме отклонения, не задаётся.

## Целостность данных

* Внешние ключи `ON DELETE CASCADE`: удаление пользователя удаляет его пробы, пробы/методики удаляют исследования,
  исследования удаляют измерения. Висячих ссылок не остаётся.
* Ограничения в БД: уникальность e-mail и названия методики (без учёта регистра), одна методика на пробу не более
  одного раза, `min_value <= max_value`, `max_spread >= 0`, допустимые значения статусов, у завершённого
  исследования всегда есть среднее.
* Правила, затрагивающие несколько таблиц (материал пробы = материал методики, значение в диапазоне методики,
  разброс подтверждённых измерений), проверяются в сервисах внутри транзакции (`@Transactional`) с пессимистичными
  блокировками строк (`SELECT ... FOR UPDATE`) и единым порядком блокировок «проба -> исследование».
  Нарушения возвращаются как `400` (некорректные данные) или `409` (недопустимо в текущем состоянии).
* Итоговое среднее исследования считается только по подтверждённым измерениям.

## Бизнес-операции

| Операция | Затрагивает | Правила и результат |
|---|---|---|
| `POST /api/samples/{id}/order-analyses` | проба, методики, исследования | Создаёт исследования по всем методикам для материала пробы, которые ещё не назначены; проба -> `IN_PROGRESS`. `409`, если проба завершена/отклонена, нет методик для материала или всё уже назначено |
| `POST /api/samples/{id}/reject` | проба, исследования | Отклоняет пробу, незавершённые исследования -> `CANCELLED`, завершённые и измерения сохраняются. `409` для завершённой или уже отклонённой пробы |
| `POST /api/analyses/{id}/confirm-measurements` | исследование, измерения, методика | Подтверждает все неподтверждённые измерения и пересчитывает среднее. Всё или ничего: если разброс превысит норму методики, не подтверждается ни одно. `409`, если исследование не `IN_PROGRESS` или подтверждать нечего |
| `POST /api/analyses/{id}/complete` | исследование, измерения, проба | Нужно хотя бы одно подтверждённое измерение и разброс в норме. После завершения измерения исследования менять нельзя. Если завершены все исследования пробы, проба -> `COMPLETED` |
| `POST /api/analyses/{id}/reopen` | исследование, проба | Возвращает завершённое исследование в работу, проба -> `IN_PROGRESS`. `409`, если исследование не завершено или проба отклонена |

## Архитектура

* `controller`: HTTP, маппинг в DTO (`dto`), коды ответов;
* `service`: бизнес-правила, расчёты, транзакции;
* `repository`: Spring Data JPA (доступ к БД);
* `model`: JPA-сущности; `exception`: единый обработчик ошибок (`404`, `400`, `409`).

Текущее время задаёт сервер (`Clock`), из запросов оно не принимается.

## Запуск

1. Необходимо установить PostgreSQL и JDK 21.
2. Выполните скрипты из `db/` от суперпользователя `postgres`
   ```
   psql -U postgres -f db/01_roles_and_database.sql
   psql -U postgres -d lab_db -f db/02_schema.sql
   psql -U postgres -d lab_db -f db/03_privileges.sql
   psql -U postgres -d lab_db -f db/04_seed.sql
   psql -U postgres -d lab_db -f db/05_authentication.sql
   ```
   Важно: повторный запуск `db/04_seed.sql` очищает бизнес-таблицу `users`; из-за внешнего ключа `ON DELETE CASCADE` будут удалены и связанные записи `app_accounts`. Скрипт `db/06_account_management.sql` содержит примеры ручного назначения ролей и изменения состояния аккаунта;
   это справочник команд, выполнять его целиком не требуется.
   Приложение подключается пользователем `lab_app`, у него только `SELECT/INSERT/UPDATE/DELETE`: создавать
   и менять таблицы он не может.
3. Скопируйте `.env.example` в `.env` и укажите тот же пароль.
4. Запустите: `./mvnw spring-boot:run` (на Windows `mvnw.cmd spring-boot:run`). Сервис доступен на `http://localhost:8080`.

Тестовые данные: 3 пользователя, 3 методики, 4 пробы в разных статусах, исследования и измерения.

## Проверка

* `requests.http`: коллекция запросов для IntelliJ IDEA (CRUD по всем сущностям и 5 бизнес-операций, сквозной
  сценарий от создания данных до каскадного удаления; идентификаторы подставляются автоматически).
* `./mvnw test`: автотесты бизнес-логики.

## Аутентификация и авторизация (задание 4)

### Учетные записи

Таблица `app_accounts` предназначена для входа в приложение. При регистрации создаётся связанный заказчик и учетная запись с ролью `CUSTOMER`. Роль и состояние нельзя передать через DTO регистрации: сервер назначает `CUSTOMER` и `ACTIVE` независимо от содержимого запроса.

Пароли хранятся только как BCrypt-хеш (`BCryptPasswordEncoder`, strength 12). Требования к паролю: 12–72 байта UTF-8, заглавная и строчная буквы, цифра и специальный символ, без пробельных символов. E-mail нормализуется в нижний регистр и уникален без учёта регистра; повторное использование e-mail, уже занятого заказчиком из таблицы `users`, также запрещено.

В `app_accounts.status` предусмотрены `ACTIVE`, `LOCKED` и `DISABLED`. Вход разрешён только `ACTIVE`: `LOCKED` считается заблокированным, `DISABLED` — отключённым. Примеры SQL для блокировки, отключения и восстановления находятся в `db/06_account_management.sql`.

### Роли и правила доступа

| Роль | Разрешения |
|---|---|
| `CUSTOMER` | Просмотр только своих проб, исследований и измерений; просмотр методик; создание своих проб; заказ подходящих исследований для своих проб |
| `LAB_TECHNICIAN` | Просмотр всех данных, CRUD проб/исследований/измерений, заказ методик, подтверждение измерений, завершение/возврат исследований, отклонение проб |
| `ADMIN` | Все возможности сотрудника, а также CRUD заказчиков и управление справочником методик |

Контекстная проверка выполняется для каждой выборки заказчика. Чужая проба, исследование или измерение для роли `CUSTOMER` возвращается как `404`, чтобы не раскрывать наличие ресурса по перебору ID. При создании пробы `customerId` берётся из учетной записи; переданный клиентом чужой `customerId` отклоняется. Правила не заменяют, а дополняют предметные ограничения из сервисов задания 3 (статусы, диапазоны, разброс, порядок операций и блокировки строк).

Ролевые правила заданы через `SecurityFilterChain` и `@PreAuthorize`. Входные данные пользователя не используются для выдачи полномочий. Публичной регистрации сотрудника или администратора нет.

### HTTP Basic, CSRF и CORS

* HTTP Basic включён для API. Ошибка аутентификации возвращает `401` и `WWW-Authenticate: Basic`; доступ к запрещённому действию — `403`; бизнес-конфликт остаётся `409`, некорректный запрос — `400`, отсутствующий ресурс — `404`.
* CSRF включён для всех небезопасных HTTP-методов (POST/PATCH/DELETE и т.п.), в том числе для регистрации. Используется `HttpSessionCsrfTokenRepository` (synchronizer token pattern). Сначала вызовите `GET /api/auth/csrf`, получите `token` и сохраните cookie `JSESSIONID`; передавайте токен в заголовке `X-CSRF-TOKEN`. GET/HEAD не должны менять данные.
* CORS настроен только для явно указанных origin; нельзя сочетать credentialed requests и `Access-Control-Allow-Origin: *`. По умолчанию разрешён `http://localhost:3000`; список меняется переменной `APP_CORS_ALLOWED_ORIGINS` (через запятую). Разрешены методы GET/POST/PATCH/DELETE/OPTIONS и заголовки Authorization, Content-Type, X-CSRF-TOKEN.
* Cookie сессии имеет `HttpOnly` и `SameSite=Lax`. При HTTPS в окружении установите `SESSION_COOKIE_SECURE=true`. Для frontend на отдельном site (не просто другом порту localhost) требуется осознанно выставить `SESSION_COOKIE_SAME_SITE=none` вместе с `SESSION_COOKIE_SECURE=true` и разрешить точный origin через `APP_CORS_ALLOWED_ORIGINS`. CORS не заменяет CSRF-защиту и не является механизмом аутентификации.

### Первоначальная настройка администратора и сотрудников

Автоматического встроенного администратора и пароля по умолчанию нет. После запуска приложения:

1. В `requests.http` выполните GET `/api/auth/csrf`, затем первичную POST-регистрацию из блока «ПЕРВИЧНАЯ НАСТРОЙКА». В локальном окружении IntelliJ задайте `adminEmail`, `adminPassword`, `adminAuth`.
2. Остановите коллекцию и выполните от владельца БД команду из `db/06_account_management.sql`, заменив адрес на свой: `UPDATE app_accounts SET account_role = 'ADMIN', customer_id = NULL WHERE lower(email) = lower('...');`.
3. Укажите `adminAuth = Base64(email:password)` в `http-client.private.env.json` и запускайте основную коллекцию. Аналогично зарегистрируйте учетную запись сотрудника, затем вручную назначьте ей `LAB_TECHNICIAN`.
4. Регистрацию обычного заказчика и сценарии CUSTOMER/LAB_TECHNICIAN можно воспроизвести в частях H и I `requests.http`. Значения `customerEmail`, `customerPassword`, `customerAuth`, `techEmail`, `techPassword`, `techAuth`, `invalidAuth` задаются в локальном IntelliJ HTTP Client environment; файл с секретами добавлен в `.gitignore`.

В `requests.http` Все защищённые запросы используют `adminAuth`, а изменяющие — CSRF-заголовок. Части H–J показывают регистрацию, собственные ресурсы заказчика, запреты `403`, CSRF-отказ `403`, возможности сотрудника и ошибки `401`.

Пример записи окружения IntelliJ:

```json
{
  "local": {
    "adminEmail": "admin@example.tst",
    "adminPassword": "ReplaceWithStrongAdminPassword123!",
    "adminAuth": "BASE64_OF_EMAIL_COLON_PASSWORD",
    "customerEmail": "customer@example.tst",
    "customerPassword": "ReplaceWithStrongCustomerPassword123!",
    "customerAuth": "BASE64_OF_EMAIL_COLON_PASSWORD",
    "techEmail": "technician@example.tst",
    "techPassword": "ReplaceWithStrongTechnicianPassword123!",
    "techAuth": "BASE64_OF_EMAIL_COLON_PASSWORD",
    "invalidAuth": "BASE64_OF_EMAIL_COLON_WRONG_PASSWORD"
  }
}
```

Для Base64 заголовка `Authorization` используйте `printf '%s' 'email:password' | base64` (PowerShell: `[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes('email:password'))`). Убедитесь, что для каждой пары email/password используется соответствующее закодированное значение.
